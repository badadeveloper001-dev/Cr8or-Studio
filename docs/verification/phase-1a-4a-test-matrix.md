# Phase 1A-4A capability verification matrix

**Preparation only. NO LIVE PROVIDER TESTS PERFORMED.** Every row below is a future test with status **NOT RUN**. This document neither authorizes execution nor supplies a live harness. The [master plan](phase-1a-4a-provider-verification-plan.md), [resource authorization](phase-1a-4a-resource-authorization.md), [recovery runbook](phase-1a-4a-recovery-runbook.md) and [release checklist](phase-1a-4a-release-readiness.md) govern execution after separate owner approval.

## How to execute and record this matrix later

Run rows in order within each capability, after the **SDK-01–SDK-09, FS-01–FS-10 and ISO-01–ISO-10** compatibility tests in the [master-plan matrix](phase-1a-4a-provider-verification-plan.md#installed-sdk-and-runtime-compatibility-matrix). Those 29 tests are incorporated by reference and are not duplicated below. A failed prerequisite blocks dependent rows; keep them NOT RUN. An attempted test that cannot observe a necessary invariant is INCONCLUSIVE, not PASS; an observed violation is FAIL. Capture one evidence record per row and per parameterized variant, using the master-plan schema. A negative test passes only when the expected rejection, lack of prohibited effects, and preservation of prior data are observed.

Future harness work must keep production facades and hardcoded release gates unchanged. It must compose existing server-only mechanisms under an explicitly authorized isolated runner; a request parameter or environment override is not acceptable. All credentials, registrations and sessions are synthetic or dedicated test resources. The preparation phase creates none of them.

Prerequisite abbreviations:

- **A**: owner-approved resource IDs, financial and duration limits, cleanup scope, test harness and operator; version-pinned reviewed code; production connectivity excluded.
- **D**: dedicated disposable Daytona sandbox with SDK/filesystem/isolation prerequisites independently verified; exact ID and approved repository root recorded. Fault variants use a separately approved disposable fixture or restored fixture state, never an owner workspace.
- **G**: disposable GitHub repository with approved exact identity, dedicated server-side credential and synthetic branches. GitHub object/branch/PR results must come from the actual GitHub API. A mock is not a substitute.
- **P**: disposable PostgreSQL with already authorized test schema, synthetic owner/session, exact project/sandbox/repository registrations and applicable scoped approvals. Schema installation and credential provisioning require the later authorization; neither occurs here.
- **F**: deterministic fixture manifest recording byte counts, SHA-256 content digests, Git object IDs, branch/HEAD, original destination state and expected allowed effects. Raw source and environment values stay out of evidence.
- **X**: separately reviewed fault-injection seam in the future harness. Record exactly which response, frame, deadline or database boundary was intercepted. Injected outcomes prove application handling only, not natural provider behavior.
- **O**: independently authorized read-only observer scoped to the disposable resource, capable of checking process/resource/file state without using the operation's success receipt as its only evidence.

The current trusted naming map in [`git-project-naming.ts`](../../src/lib/security/git-project-naming.ts) contains only the application repository. **GIT-02–GIT-05 and GIT-16 require an additional prerequisite:** a separately reviewed, compiled test-only binding for the exact disposable repository in the later harness. Other Git mutation tests using the naming service share this dependency. Do not use the application repository, accept a client/model/environment project code, or change deployed naming configuration to satisfy it. Until that harness dependency is approved, these tests remain NOT RUN. The approved fixture must exercise the actual supported commit helper and numbering logic against its trusted test binding.

Unless a row narrows them, all rows require A. A row marked X is a planned hybrid/fault-injection test; its result must retain that classification. Live SDK/API transport evidence and injected-behavior evidence must be separate. Existing controlled-adapter tests are useful baselines, but cannot populate these live-provider result cells.

| Initialization | [`private-github-repository-source.ts`](../../src/lib/workspace/private-github-repository-source.ts): 300 GETs, 30 seconds, 5-second request/body waits, 1 MiB response. At-boundary success is subject to all other limits. For example, the 16-commit positive fixture must also fit 128 objects/1 MiB and complete within the overall deadline. A provider unable to satisfy the current bounded profile is a compatibility finding; do not raise limits during verification.

## Result interpretation and known limits

PASS is narrowly scoped to the observed fixture, provider version and environment. It is not a claim of general compatibility, complete host isolation or resistance to a malicious provider. Provider metadata must be corroborated by allowed runtime observations; unobservable isolation remains INCONCLUSIVE. Same-UID malicious scripts can escape process groups or attack their supervisor, so session deletion or a helper-reported cancellation flag alone does not establish descendant termination.

GitHub REST ref mutation has no atomic expected-old-SHA compare-and-swap guarantee in this implementation. Keep concurrent-writer tests, branch protection review and residual-risk acceptance separate from a successful ordinary fast-forward. Git object creation may succeed before a later failure; cancellation does not roll back created objects or refs. File writes likewise have a small final PostgreSQL-check-to-publication race. Lifecycle and initialization may finish remotely after local timeout. Preserve UNKNOWN reservations and consult the runbook rather than repeating an ambiguous operation.

All listed tests remain **NOT RUN**. No live harness, resources, credential provisioning, migration, provider test or release activation is part of this preparation.
