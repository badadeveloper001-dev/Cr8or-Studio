# Phase 1A-4A: failure and recovery runbook

**Preparation only. NO LIVE PROVIDER TESTS PERFORMED.** Every future live recovery scenario is **NOT RUN**. This document authorizes no provider access, mutation, cleanup, credential operation, database change or release-gate change. The actions below describe a future test run after the owner separately approves the [resource scope](phase-1a-4a-resource-authorization.md) and a reviewed isolated harness.

Use this runbook with the [master plan](phase-1a-4a-provider-verification-plan.md), [test matrix](phase-1a-4a-test-matrix.md) and [release checklist](phase-1a-4a-release-readiness.md). All faults must be injected into disposable fixtures. Never induce a failure in an owner workspace or application repository.

## Recovery contract

The authority is PostgreSQL session validation, immutable approval scope and the original operation reservation. A timeout, missing response, disconnected caller or stopped log stream is not evidence that external work did not happen. Observation and authorization must both succeed before an operation can be confirmed.

| Situation | Required interpretation | Permitted next step after future authorization |
| --- | --- | --- |
| Rejected before external dispatch, with positive evidence of no dispatch | Expected rejection; not an uncertain provider success | Preserve the rejection evidence. A later attempt needs valid authorization and the normal approval/reservation rules. |
| Lifecycle `RESERVED`, no dispatch attempt, deadline elapsed | May be cancelled by the existing authorized reservation-cancellation path | Confirm `attempts = 0` and the fixed deadline; cancel only that reservation. This does not create/delete/start a resource. |
| Lifecycle `DISPATCHED` or command/Git `RUNNING`, response lost or failure bookkeeping unavailable | Potential external effects; do not free coordination | Preserve the reservation. A missing `UNKNOWN` update does not make the operation retryable. |
| `UNKNOWN` | Unresolved external effects or missing termination/cleanup evidence | Stop scheduling against the affected reservation and use bounded read-only diagnosis. No automatic retry, replacement, remap or deletion. |
| Confirmed nonzero exit, confirmed termination and cleanup | Operation failed, not successful | Record the actual exit status without sensitive output; follow the normal policy for any separately approved new operation. |
| All required state, identity, authorization and cleanup evidence agrees | Candidate confirmed completion | Only the applicable existing reconciliation/completion path may update test database state. Test PASS also requires the evidence and cleanup criteria. |

An application status and a test verdict are different. A fault-injection test can PASS because the operation correctly remains `UNKNOWN`. The resulting resource must still be inventoried and must not be described as clean or ready. An unexplained or unobservable outcome is INCONCLUSIVE, not PASS. A demonstrated violated invariant is FAIL.

## Initial response to any failure

1. Stop the affected test sequence and suppress subsequent mutations and output release. Do not submit a new idempotency key to escape a retained reservation.
2. Record the test ID, operation ID, canonical project and registration identifiers, expected provider ID/repository/branch/SHAs, approved scope digest, timestamps, last confirmed phase and sanitized failure category. Use a local evidence alias for the initiating session; never copy its raw token, digest or credential values.
3. Record separately whether dispatch, publication, remote branch update, process termination, command-session deletion and database persistence were confirmed. An SDK promise rejecting proves none of these by itself.
4. Inspect only the allowlisted disposable resource and test database. Compare the original reservation, exact returned resource ID and immutable operation metadata. Never use a friendly name as ownership proof.
5. Apply the scenario below within its observation budget. Stop when the budget, authorization, test-duration or cost limit is exhausted. Escalate an unresolved record to the owner; do not loop until a favorable response appears.
6. Preserve an evidence copy before any separately approved cleanup. If credentials may have escaped, halt the run and follow the exposure procedure in the resource checklist; do not paste the suspected value into the report.

Exactly one matching resource with verified identity, labels, isolation and required state is necessary. Zero, duplicate, contradictory or excessive matches remain unresolved. Existing or unexpected files are never overwritten. | NOT RUN |
| Repository is absent or initialization incomplete | Preserve the reservation and sandbox; report the inspection classification. Escalate for a later reviewed recovery assignment. | NOT RUN |
| Repository has an unexpected HEAD, changed remote branch or changed sandbox ID | Deny completion. | GitHub object upload succeeds but branch update fails | Preserve `UNKNOWN` once remote mutation was attempted and its full outcome is unverifiable. | Draft PR creation succeeds but verification fails | Preserve uncertainty; fetch only the specific returned PR if its identity is available and in scope. Validate repository, head/base names and SHAs, title, open state and draft flag. | No automatic recreation, title modification, closure or merge, even if readback later becomes available. | Command timeout, disconnect or cancellation cannot confirm termination | Stop scheduling and withhold further command output. | Session expires, is revoked or credential generation changes | Deny subsequent provider dispatch, transfer commit, mutation and output release when invalidation is detected. Do not reuse an old approval under a newly authenticated session. | Timeline of last database validation, invalidation, attempted next step and absence of unauthorized output. Publication already completed is not rolled back. | NOT RUN |
| Network connection or provider SDK call fails | Record the last confirmed phase. A client timeout bounds waiting but may not cancel the remote operation. Retain `UNKNOWN` after possible dispatch; use only the bounded read-only checks allowed for that operation. | No inferred success/failure from timeout alone, no automatic provider retry and no alternate token, sandbox or local-host fallback. | NOT RUN |

## What the existing reconciliation actually supports

The current implementation is intentionally narrower than a general administrator recovery tool:

- [Lifecycle service](../../src/lib/workspace/private-workspace-lifecycle.ts) reconciles by inspecting the original resource. It never retries create/start/stop/clone, deletes resources or changes identity. Existing start reconciliation requires isolation as well as `started`; create/clone also require exact creation labels. Clone readiness additionally requires independent repository inspection.
- [Lifecycle store](../../src/lib/security/workspace-lifecycle-store.ts) binds operation access and completion to the initiating owner session and credential generation. Reconciliation applies to `UNKNOWN` or an expired `DISPATCHED` record, with at most three claims and at least 60 seconds between claims. Each failed observation consumes an attempt. One claim permits only bounded completion evidence, not a provider mutation. A `RESERVED` record is cancellable only before dispatch (`attempts = 0`) after its 60-second deadline.
- [Repository transport](../../src/lib/workspace/private-repository-initialization.ts) validates the complete source again as needed and checks that the approved source branch still points to the approved HEAD, including during inspection. Revoked/expired initiating sessions, credential rotation, a changed remote HEAD or exhausted reconciliation attempts therefore require a separately designed and reviewed operator process; a fresh login alone does not adopt the operation.
- [Command store](../../src/lib/security/command-operation-store.ts) and [Git store](../../src/lib/security/git-operation-store.ts) retain shared workspace slots for `UNKNOWN`. Their finish/cleanup APIs cannot clear that state. Do not fabricate a success receipt or directly edit rows to bypass this rule. The current implementation has no general command/Git operator-reconciliation endpoint.
- Database housekeeping is not provider cleanup. Lifecycle housekeeping retains all operation receipts and consumed approvals; command/Git housekeeping never deletes unresolved operations. No housekeeping step frees an uncertain provider resource by assumption.

## Safe historical shutdown versus safe startup

The [provider adapter](../../src/lib/workspace/private-lifecycle-provider.ts) permits a separately authorized stop of an exactly bound historical sandbox without asserting that its legacy isolation is suitable for private development. A transition to stopped still requires protection against destructive auto-delete/auto-destroy behavior; unsafe settings cause rejection and are not repaired. An already-stopped result is not permission to execute in that resource.

Start requires exact identity and verified isolation before dispatch, revalidation immediately before dispatch, and fresh identity/state/isolation verification afterward. Already-started resources must pass the same readiness checks. Stopping is not a workaround for failed identity checks. This preparation must not inspect or modify historical owner resources; the distinction is tested only with controlled disposable metadata fixtures in the later authorized run.

## Cleanup and escalation rules

The existing operation budgets remain authoritative: command-session cleanup is bounded to five seconds, repository-session cleanup to five seconds with bounded polling, and lifecycle provider calls to five seconds per SDK request within a 30-second provider operation and 60-second lifecycle deadline. Stage ceilings are not additive promises that exceed the enclosing deadline. A provider call can complete after the application stopped waiting.

Future cleanup must use the exact approved inventory, confirm no continuing operation needs the fixture, and record separate outcomes for process termination, session deletion, temporary storage cleanup, sandbox stop/delete, repository retention/delete and test-credential revocation. Resource deletion is not implemented by the application lifecycle service and needs an explicit, separately reviewed test-cleanup procedure. Automatic shutdown, provider TTL or an empty application response is not proof of deletion.

Escalate before any action that would change approval scope, replace/remap a resource, alter a retained database record, retry a dispatched mutation, delete uncertain data, change network/isolation configuration or exceed the approved cost/time limit. Record the exact unresolved question and the evidence needed; do not grant recovery authority through this document.

## Runbook acceptance

For each future failure test, retain the original operation/approval identity, observed state transitions, count of mutation dispatches, absence of unauthorized subsequent work, sanitized independent evidence and final cleanup disposition. Cross-instance retries must not create a second side effect. Failure to observe a required invariant is INCONCLUSIVE; an invariant violation is FAIL. No recovery scenario is currently verified against live providers: **NOT RUN**.
