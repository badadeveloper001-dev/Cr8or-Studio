# Phase 1A-3F: Git naming consistency

This targeted correction follows `b0d43990bf2b52d999e09f69ac5a9550447cc6fe`
on existing draft PR #8. All private Git operations remain release-blocked.
The missing local-object upload transport is unchanged and is simulated only in
isolated tests. No migration, project identity change or workspace provisioning
is introduced.

## Inconsistency and convention

The local helper generated `PROJECT-NNN` commits, while the PR transport searched
for `CR8OR-NNN` and added another number. Its own commit output therefore could
not reliably advance the PR sequence. Merely changing the prefix would still
leave the PR using a number that the next commit could allocate again.

The correction uses **one shared change identifier**. A new commit allocates the
next trusted project number. Its corresponding PR reuses that exact identifier
and neutral title; PR creation never allocates another number. A commit/PR pair
represents one change, so that intentional reuse is not a duplicate. A different
commit or second PR with the same identifier is rejected.

| Cycle | Commit generated by the helper | Corresponding draft PR |
| --- | --- | --- |
| First | `CR8OR-001: Code improvements` | `CR8OR-001: Code improvements` |
| Next | `CR8OR-002: Test improvements` | `CR8OR-002: Test improvements` |

Numbers are monotonic; gaps are allowed when commits do not receive PRs. The
server-owned registry is the only source of project codes. Its reviewed entry
maps the canonical CR8OR repository to `CR8OR`; unknown naming mappings fail
closed. Clients and models cannot supply a code, sequence, title or naming rule.

## Commit generation

The same frozen registry is embedded into the fixed-purpose Python helper. The
helper independently checks that the server's metadata prefix matches the
verified repository. It does not infer a code from arbitrary Git history or
environment variables. Session results must contain the exact trusted code,
canonical number and approved neutral category.

Local allocation scans SHA and subject across all available refs. It rejects
different commits using the same namespace/number, zero, alternate padding,
overflow, malformed identifiers and unsupported/incomplete histories. Repeated
references to the same commit are allowed. The scan is limited to 1,000 commits,
the existing 256 KiB output bound and operation deadline; refs and expected
HEAD/index are checked again before mutation.

Historical `PROJECT-NNN` commits are never rewritten. Their highest number is
reserved as a legacy floor within this repository. New commits use one plus the
maximum trusted-code or legacy number. For example, a legacy `PROJECT-007`
history can produce `CR8OR-008`, then a corresponding `CR8OR-008` PR. Unrelated
prefixes neither choose the trusted code nor influence allocation. Duplicate
checks apply within each namespace; historical legacy/project prefixes remain
distinct records.

The GitHub file-update path uses the same trusted code and legacy floor. Its
server adapter verifies returned naming metadata, and the low-level transport
rechecks the proposed commit message against complete current history before
PUT. A stale proposed number is rejected rather than replaced.

## Approval and PR verification

Create-PR scopes now bind naming version `2`, strategy `approved-head-commit`,
and the trusted code. The existing scope also binds the exact immutable head SHA,
head/base branches and SHAs, category, repository, project and workspace. The
head commit's canonical subject must match the approved category exactly; that
subject is the intended PR title. No title is calculated from mutable PR state.

Commit and file-update scopes add `commitNaming` version `1` with strategy
`registered-history-next`. These fields bind the code and allocation rule along
with existing expected repository state and operation data. Old PR, commit and
file-update scopes lacking the current naming contract cannot be consumed or
silently upgraded. Their audit records are retained. Unrelated approvals retain
their existing shape and behavior.

Before PR dispatch, bounded complete head/ref histories must prove that the head
has the unique highest trusted identifier and exceeds the legacy floor. Existing
open or closed PR identifiers must be unique and lower. New conflicting remote
state rejects the approval; it never selects a different title. The owner must
review an appropriate new head and request a new approval when the old candidate
is stale. Session, credential-generation, ten-minute lifetime and one-time
consumption checks remain unchanged.

Both creation and fetched responses still require exact title, repository,
branches, head/base SHAs, open state and `draft: true`. Postflight checks and
`UNKNOWN` coordination behavior remain intact. There is no automatic PR retry,
modification, closure or merge.

## Cross-component regression

The new consecutive-cycle suite modifies real files and invokes the actual
private Git session and Python helper to stage and create both numbered commits.
It builds immutable remote-response snapshots from those actual Git objects to
simulate the missing upload boundary. The real GitHub adapter factory and
transport then create and verify matching draft PRs using controlled fetch.
The test does not seed manually invented CR8OR-numbered commits.

The positive cycle simulates the owner externally closing the first PR before
the next one uses the same head/base pair. Its identifier remains reserved.
The controlled provider rejects a duplicate open pair, matching GitHub's behavior;
the negative case remains `UNKNOWN` without corrective mutations. No application
code closes or merges a PR. Original commit SHAs, ancestry and UTF-8 contents
are checked after both cycles.

## Remaining limits

- Local refs cannot prove that all remote history has been fetched. Historical
  PR-only allocations and external PRs ahead of local commits can still cause a
  stale PR rejection; they are never silently renumbered. Synchronization and
  historical numbering reconciliation require separate review before release.
- Squash/rebase histories can introduce distinct commits with the same change
  identifier. Such histories fail closed rather than being rewritten or guessed.
- GitHub does not provide atomic custom-title reservation across external actors.
  Snapshot checks detect observed races but cannot eliminate them. Existing
  PostgreSQL coordination serializes this application's conflicting mutations.
- Complete-history/ref/PR bounds remain conservative. Larger or incomplete
  repositories are denied, and only the reviewed CR8OR naming map is configured.
- A subsequent PR needs prior closure/merge or a separately authorized distinct
  branch. This task does not automate those actions or implement object upload.

These dependencies keep the hardcoded Git release restriction necessary. The
cloud-write and command-execution restrictions, inactive production authentication,
project IDs, GitHub references, Daytona IDs and existing history remain unchanged.
